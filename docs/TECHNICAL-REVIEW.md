# Engineering review — 22 October 2026

## Verdict

Portion has a substantive prototype: contract accounting, a typed SDK, native transaction builders, wallet-owned signing, indexing/gateway services and a polished frontend. The complete equipment-funding product is not operational. No Portion deployment configuration exists, the smaller contract candidate is not integrated, public backend services are not hosted, and real wallet/asset lifecycle evidence is absent.

This is a focused source and regression-test review, not an independent security audit or commercial validation. Review baseline: `7b17750`. The corrections below do not change deployed contracts or submit transactions.

## Development sequence and completion criteria

1. **Trustworthy foundations — this change.** Finalized receipts, accepted document records, honest backing checks, replay-safe finalized indexing and visible build status. Regression tests and build/type checks must pass.
2. **One integrated contract path.** Implement the Core adapter and document/event schema, test all web intents against it, resolve the funding gap, deploy only after measured costs fit. Completion requires verified addresses/code, configured payment asset, and actual extension-signing evidence.
3. **One usable lifecycle.** Host persistent services. Operator supplies real asset details, participant reviews and purchases, operator deposits, participant claims. Preserve finalized receipts and exact balance changes, handle rejection/partial upload/unknown outcome, and verify document expiry/renewal. No generated visitor wallets or invented assets.
4. **A pilot people can judge.** Add operator evidence, visible fees, actual payment history, downloadable receipts and clear exit/default information. Validate one reachable operator first while keeping the product global. Then add broader wallet support and secondary tools where customers need them.

## Features worth adding

- An operator evidence checklist: operator identity, asset documents, business revenue source, payment schedule, verification date and who checked what. Keep self-reported, chain-checked and independently verified information distinct.
- A receipt/history centre: finalized hash, action, fees, balance changes, pending/failed/unconfirmed states, and export. Never offer a blind retry when the previous outcome is unknown.
- A clear first-use journey: select operator or participant intent without generating accounts; show prerequisites and direct the user to the next available action.
- A revenue breakdown using actual deposits: gross payment, contract fee and participant allocation. Separate operator promises from deposited income and any estimate.
- A deliberate default/exit process: what happens when payments stop, who can act, how bond allocation works, and what selling or unstaking does and does not return.

## Verification scope

Contract unit/fuzz suites, SDK receipt/storage tests, native-proof/indexer regressions, web data-integrity tests, type checks, production build and browser checks support this change. Test doubles are isolated test fixtures. Dependency audit reports no known production-dependency advisories at review time; that is not evidence the application is vulnerability-free.

The refreshed budget report is read-only and records no submitted transactions. Live contract deployment, live extension signing, real asset payment/claim execution, hosted service durability and an independent security review remain outstanding.
